# thai-sme-pos

Direction: e-commerce system for Thai SMEs. The React app in `src/` is an early cafe-POS prototype; the active work is `ads-engine/` and `ads-web/`.

## Working rules (Benz 2026-10-15: keep the work orderly before adding more)

- **Simple first.** One page per job, one link bar on every page (`ads-web/web/src/SiteNav.tsx`; a new page goes in it). Say on the page where each number comes from in one line. Prefer fixing and finishing what exists over a new feature; ask Benz before starting a new area.
- **One session, one area, its own copy.** Several Claude sessions work on this repo at once. Work in your own git worktree (`git worktree add`), not in the shared folder; commit small and push to `ads-web`. If you must use the shared folder, stage only your own lines.

Never deploy uncommitted or someone else's half-done work. New migration = next free number (check `ls migrations` and `wrangler d1 migrations list DB --remote`).
- **Anything that writes outside ships switched off.** Meta (budgets, statuses, conversions), Page365, messages to customers or a new Discord channel: build it with a dry run, show Benz the dry-run output, and let Benz switch it on. ## ads-web (dashboard + scheduler on Cloudflare, Workers Paid since 2026-10-22)

- Worker + D1 + React (`ads-web/README.md` has deploy steps). Imports ads-engine's `rules.ts`, `apply.ts`, `meta.ts`, `notify.ts` directly — change rule logic there, not in a copy.
- Two axes per campaign. **Stage** (`stages` table, fixed four: experiment / testing / winning / retest) is set by Benz and carries the rules; no stage = never automated. **Product section** (keyword in campaign name, or pinned) links sheet product codes → break-even ROAS; rules use `value_mode: "x_breakeven"` so one stage rule set fits every product. Engine groups by stage × section.
- Profit is counted per piece, not per order: one ad sells several promos (1 for 189, 3 for 549) and Meta only reports orders + value. Pieces ≈ value ÷ price per piece (promos in the campaign name, e.g. "1 ตัว 189 (3ตัว549)", plus section `tiers`; else manual price; else cost column I); sheet cost is all-in (shipping + returns), so no per-order extra by default. Pieces/profit are a range; rules use the conservative end. COD +50: not added (counted only if admins include it in the tagged value).
- Stage rules (installed 2026-10-12, live since 2026-10-13 08:00 at Benz's request; a product line without its own break-even uses the shop-wide one from the last 14 days of Page365 orders, 1 ÷ gross margin ≈ 2.9): thresholds are multiples of each product's break-even (`x_breakeven`), 3-day windows for budget moves, 7-day for stage moves, every cut needs real spend first (≥ 3×/5× CPA ≈ 450/750), tiered cuts −20% soft / −20%+−20% hard / move to retest when < 0.5× BE; guardrails 20%/run, 50–3,200 per campaign (proven winners — winning stage, real 7-day ROAS ≥ 1.5× shop BE, ≥ 10 orders — up to `guardrails.winner_max_daily_budget`, default 5,000; Benz 2026-10-22); one increase per campaign/ad set per `guardrails.increase_gap_hours` (default 48; budgets under `free_increase_below`, default 500, rise every run; whichever rule raises; cuts and copy ramps exempt; `spaceIncreases` in run.ts) so the 3-day ROAS reflects the new budget before the next raise; above 3,200, one bad day (yesterday ROAS < 0.8× shop BE on ≥ 2,000 spend; real if that day's file is uploaded, else Meta's) pulls the budget straight back to 3,200 and holds raises 48 h (`yesterdayBrakes`, `guardrails.brake_yesterday` off/dry/on, ships 'dry' = Discord note only until Benz switches it on); the total/day cap is whatever Benz sets on the Settings page (20,000 as of 2026-10-15, read from D1 `settings.guardrails`, not this file) and it only blocks increases — cuts always go through; the Monday cap check (Goal below) proposes +20% when real 7-day MER ≥ `scale_mer`. The same set is in `ads-web/web/src/stageTemplates.ts`. Target structure: product cost ~52% of revenue, per-order fees ~12.5%, gross ~35% → ads ≤ 25% for ~10% net.
- Rules decide on real sales (from 2026-10-14 20:00, Benz's call): `worker/actualMetrics.ts` swaps a campaign's Meta-tagged purchases/value for the orders Page365 credited to it, day by day, for every uploaded day of yesterday/last_3d/last_7d/last_14d (spend stays Meta's; not-yet-uploaded days and ad-set metrics stay Meta's). A day whose orders are < 80% credited keeps Meta's numbers. Run notes and Discord questions say which source was used. Baseline 11–13 Oct: Meta 268 purchases / 105,938 vs Page365 235 orders / 95,403 (211 credited) — Meta tags run ~11–14% high, so real ROAS is lower, most on the 501 campaigns.

## ads-engine (Meta Ads, rule-based)

- Zero-dependency Node 24 TypeScript. `cd ads-engine && npm run run` = dry run, `npm run apply` = change budgets for real, `npm test` = rule logic tests.
- Talks to the Meta Marketing API directly with a System User token in `ads-engine/.env` (gitignored). No LLM in the daily loop — keep it that way.
- Rules are data in `ads-engine/rules.json`. Guardrails there cap budget moves; `KILL_SWITCH=true` in `.env` stops everything.
- `.github/workflows/ads-engine.yml` runs it manually (schedule moved to ads-web).

Division of labour: ads-engine runs the if/then rules; Claude (via the `meta-ads` MCP) is for ad-hoc questions, reading `ads-engine/logs/`, and proposing edits to `rules.json`. Any change that can start spend (ENABLED status, budget increases) needs explicit approval from Benz.
