# thai-sme-pos

Direction: e-commerce system for Thai SMEs. The React app in `src/` is an early cafe-POS prototype; the active work is `ads-engine/` and `ads-web/`.

## ads-web (dashboard + scheduler on Cloudflare, free plan)

- Worker + D1 + React (`ads-web/README.md` has deploy steps). Imports ads-engine's `rules.ts`, `apply.ts`, `meta.ts`, `notify.ts` directly — change rule logic there, not in a copy.
- Two axes per campaign. **Stage** (`stages` table, fixed four: experiment / testing / winning / retest) is set by Benz and carries the rules; no stage = never automated. **Product section** (keyword in campaign name, or pinned) links sheet product codes → break-even ROAS; rules use `value_mode: "x_breakeven"` so one stage rule set fits every product. Engine groups by stage × section.
- Profit is counted per piece, not per order: one ad sells several promos (1 for 189, 3 for 549) and Meta only reports orders + value. Pieces ≈ value ÷ price per piece (promos in the campaign name, e.g. "1 ตัว 189 (3ตัว549)", plus section `tiers`; else manual price; else cost column I); sheet cost is all-in (shipping + returns), so no per-order extra by default. Pieces/profit are a range; rules use the conservative end. COD +50: not added (counted only if admins include it in the tagged value).
- Stage rules (installed 2026-10-12, live since 2026-10-13 08:00 at Benz's request; a product line without its own break-even uses the shop-wide one from the last 14 days of Page365 orders, 1 ÷ gross margin ≈ 2.9): thresholds are multiples of each product's break-even (`x_breakeven`), 3-day windows for budget moves, 7-day for stage moves, every cut needs real spend first (≥ 3×/5× CPA ≈ 450/750), tiered cuts −20% soft / −20%+−20% hard / move to retest when < 0.5× BE; guardrails 20%/run, 50–3,200 per campaign, 10,800 total/day (raise 20%/week only if real 7-day MER ≥ 3.5). The same set is in `ads-web/web/src/stageTemplates.ts`. Target structure: product cost ~52% of revenue, per-order fees ~12.5%, gross ~35% → ads ≤ 25% for ~10% net.
- Rules decide on real sales (from 2026-10-14 20:00, Benz's call): `worker/actualMetrics.ts` swaps a campaign's Meta-tagged purchases/value for the orders Page365 credited to it, day by day, for every uploaded day of yesterday/last_3d/last_7d/last_14d (spend stays Meta's; not-yet-uploaded days and ad-set metrics stay Meta's). A day whose orders are < 80% credited keeps Meta's numbers. Run notes and Discord questions say which source was used. Baseline 11–13 Oct: Meta 268 purchases / 105,938 vs Page365 235 orders / 95,403 (211 credited) — Meta tags run ~11–14% high, so real ROAS is lower, most on the 501 campaigns.
- Goal (Benz 2026-10-14): 100,000 net/month (first 120,000, lowered the same day as more reachable) (revenue − product cost − per-order fees − ads; fixed costs not included). `worker/goal.ts` + `settings.goal` {monthly_net, scale_mer 3.86, scale_pct 20}; overview card + `/api/goal` + a line in the 07:30 Discord digest. The 3.86 is the MER a ~35.9% gross margin needs for 40,000/day revenue to net 4,000/day. Weekly cap check (Monday 08:00 run, or the Settings button): real 7-day MER (≥ 6 uploaded days) ≥ scale_mer → a `cap` proposal in Discord to raise `guardrails.max_total_daily_budget` +20% (rounded to 100), applied only on a button press; open 6 days. Below it → a note only.
- Post ideas for Max (`worker/postIdeas.ts`, Monday + Thursday 08:00 after the run, or Settings button; `GET /api/post-ideas` previews): product families from Page365 item names ("501/2 …" → 501), last 14 days of real orders. Ideas: real ROAS ≥ 1.25× shop break-even with ≥ 1,000 spend → new posts; sells but no campaign named for it → own test post; ROAS < break-even → no new posts; plus the promo (1/2/3+ pieces) with the best net per order. ## ads-engine (Meta Ads, rule-based)

- Zero-dependency Node 24 TypeScript. `cd ads-engine && npm run run` = dry run, `npm run apply` = change budgets for real, `npm test` = rule logic tests.
- Talks to the Meta Marketing API directly with a System User token in `ads-engine/.env` (gitignored). No LLM in the daily loop — keep it that way.
- Rules are data in `ads-engine/rules.json`. Guardrails there cap budget moves; `KILL_SWITCH=true` in `.env` stops everything.
- `.github/workflows/ads-engine.yml` runs it manually (schedule moved to ads-web).

Division of labour: ads-engine runs the if/then rules; Claude (via the `meta-ads` MCP) is for ad-hoc questions, reading `ads-engine/logs/`, and proposing edits to `rules.json`. Any change that can start spend (ENABLED status, budget increases) needs explicit approval from Benz.
