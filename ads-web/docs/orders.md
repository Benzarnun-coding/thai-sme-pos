# Order notes → Page365 bills → Meta purchases

How an admin's order note in the chat becomes a filled Page365 bill and a Purchase in Meta. Code: `worker/orderNotes.ts`, `worker/p365fill.ts`, `worker/autoFill.ts`, `worker/addressReader.ts`, `worker/thaiAddress.ts`, `worker/metaPurchases.ts`, `worker/notePurchases.ts`, `worker/metaAdjust.ts`; page `web/src/OrderNotes.tsx` (tab "Log ออเดอร์แชท"), settings card `web/src/MetaPurchases.tsx`.

## Filling bills
Filling Page365 orders automatically (Benz 2026-10-15; no computer left on, so server-side). Today: Meta AI chats → an admin opens a draft (ร่าง) and types an order note in the chat ("501/1/2/3 32\ncod 649", "ni9-3 32 1 cod 239": codes [/colours], size, optional qty; payment + total) → a second admin picks the same items from Page365's album and moves the bill on. Page365 product names start with that code and variant SKUs are `5011-PK-MD-30` (code without / and -). Phase 0 (shadow, nothing written to Page365): webhook subscribes `message_echoes`, `worker/orderNotes.ts` keeps only echoes that are nothing but a note (`order_notes`, + name hash) and compares them with the uploaded Page365 export (same customer within 24 h, else unique total within 3 h) → dashboard tab "Log ออเดอร์แชท" (`web/src/OrderNotes.tsx`: last 7 days with counts, newest first, today refreshed every minute, "รอไฟล์ Page365" until the export is uploaded) + counter on the webhook card. Each line is matched to the catalog by code + size (`catalogFor`, index `catalog_code`; PK warehouse first); 2026-10-15: 63/76 lines matched — 009-1/009-2 exist in Page365 but not in the SKU+Price sheet, and NI9 has no size 31 (the note was wrong). Next: Page365 has no public API but its web app (cookie session on page365.net, `credentials: include`, 401 → `/session/guard`, request keys snake_cased) uses JSON endpoints: GET `/{page}/orders/{id}.json`, `/conversations/{id}.json` (messages; `customer_fbid` = our Messenger PSID), `/products.json?page=` (751 products, variants carry `code` = our SKU and stock), `/products/{id}.json`; writes POST `/{page}/order_items.json` {order_id, product_ids} (adds each product with its first size), PUT `/{page}/orders/{id}.json` {order: {stage, shipping_cost, discount, …}, order_items: [{id, name, note, price, quantity, product_id = variant id}]}, PUT `/{page}/orders/{id}/advance.json` (the app's "save and send": next stage + sends the bill to the customer), PUT `/{page}/orders/change_stage.json` {orders, stage}. The team prices items at Page365's list price, COD shipping 50, and the promo gap as the bill's discount (3 × 199 + 50 − 98 = 549). Phase 1 (deployed 2026-10-15, `worker/p365fill.ts`): "ใส่ใน Page365" button per note in the Log tab → plan (customer's draft by `customer_fbid` = PSID among drafts ±12 h; product by name starting with the code, variant by SKU ending -size; checks: draft empty, found, in stock, total ≥ 0 discount ≤ 50%, COD matches, no product twice) → on press: add items, set size/qty/price/shipping/discount, read back and compare; the draft stays a draft and an admin still presses save-and-send in Page365 (`advance` is never called). Needs Worker secret `P365_COOKIE` (Cookie header of a logged-in page365.net session, ideally a separate low-rights admin) — set by Benz, never by Claude; first real fills #29349 and #29323 on 2026-10-15, checked in Page365. Phase 2 (Benz 2026-10-15): the plan also checks the note's total against the last "ยอด/รวม … N" the shop wrote in the chat (`chatTotal`; equal or note = chat + COD 50, else stop — the chat price wins), sets the bill name "PK-9349 <recipient>" (warehouse of the first SKU, CN → C, last 4 digits of the bill), and fills the address: Page365's own if complete and clean, else read from the chat by Claude (`worker/addressReader.ts`, typed text + the customer's last 3 photos by URL, structured output; `claude-opus-5-5` at low effort, `ADDRESS_MODEL` to change; the org key needs `ANTHROPIC_WORKSPACE_ID` and doesn't allow the server-side-fallback beta); the admin can correct it in the dialog. Problems stop; warnings (no agreed price in chat, address incomplete/doubtful, tiny discount) allow a single fill but are skipped by "ใส่ทุกใบที่ผ่าน" (browser loops plan → fill). Dry run 15 Oct: 11 of 15 open drafts passed. Addresses are never stored on our side. Missing postcodes (and short province names like นม, typos like ปมุมธานี) are filled/checked from the subdistrict with a built-in address book (`worker/thaiAddress.ts`, data `worker/data/thaiAddressData.ts` from kongvut/thai-province-data, MIT, 7,436 subdistricts; regenerate, don't hand-edit) — for chat-read addresses and for Page365's own; writing via a stored session needs Benz's go-ahead, a low-rights account, and the save requests seen once while an admin does an order. Also ask Page365 for an official API.

## Purchases to Meta
Purchases to Meta from Page365 orders (`worker/metaPurchases.ts`, Benz 2026-10-15: admins stop tagging sales in Meta's inbox once it is live): Conversions API for Business Messaging, POST `/{dataset}/events` with event Purchase, action_source business_messaging, messaging_channel messenger, user_data {page_id, page_scoped_user_id = Page365 `customer_fbid`}, value = bill total THB, event_time = bill opened (keeps hourly crediting in line), event_id `p365-<no>`. Counts: COD from stage unpaid (bill sent), transfer from transferred/paid. Runs from webhook deliveries at most every 10 min (no cron), ≤30 order look-ups per run, last 7 days; table `meta_purchases`, settings `meta_capi` (mode off/test/live, dataset_id, test_code, live_from = when live was switched on — earlier orders were tagged by hand) on the settings page, dry run button. Blocked 2026-10-15: the token has no `page_events` and sees no dataset (`GET /api/meta/datasets`); keep admins tagging until live.

**At the note (default source, Benz 2026-10-15):** the sale is sent seconds after the admin types the note, so it lands on the day/hour the customer agreed (the admins' own "Create order" in Meta's inbox happened at that moment too; sending at the bill put sales on the next day). event_time = note time, value = the note's total, event_id `note-<mid>`, one sale per customer per 2 hours; table `note_purchases`; setting `meta_capi.source` = note | bill (bill = the older bill-stage sender). Preview on the settings card ("ดูว่าวันนี้จะส่งอะไร"); sends only in live mode, which Benz switches on together with telling admins to stop pressing Create in Meta's inbox. Meta has no API for its inbox orders ("Manage Orders"), so that list stays empty once admins stop; a page of our own for Max is proposed.
