# Order notes → Page365 bills → Meta purchases

How an admin's order note in the chat becomes a filled Page365 bill and a Purchase in Meta. Code: `worker/orderNotes.ts`, `worker/p365fill.ts`, `worker/autoFill.ts`, `worker/addressReader.ts`, `worker/thaiAddress.ts`, `worker/metaPurchases.ts`, `worker/notePurchases.ts`, `worker/metaAdjust.ts`; page `web/src/OrderNotes.tsx` (tab "Log ออเดอร์แชท"), settings card `web/src/MetaPurchases.tsx`.

## Filling bills
Filling Page365 orders automatically (Benz 2026-10-15; no computer left on, so server-side). Today: Meta AI chats → an admin opens a draft (ร่าง) and types an order note in the chat ("501/1/2/3 32\ncod 649", "ni9-3 32 1 cod 239": codes [/colours], size, optional qty; payment + total) → a second admin picks the same items from Page365's album and moves the bill on. Page365 product names start with that code and variant SKUs are `5011-PK-MD-30` (code without / and -). Phase 0 (shadow, nothing written to Page365): webhook subscribes `message_echoes`, `worker/orderNotes.ts` keeps only echoes that are nothing but a note (`order_notes`, + name hash) and compares them with the uploaded Page365 export (same customer within 24 h, else unique total within 3 h) → dashboard tab "Log ออเดอร์แชท" (`web/src/OrderNotes.tsx`: last 7 days with counts, newest first, today refreshed every minute, "รอไฟล์ Page365" until the export is uploaded) + counter on the webhook card. Each line is matched to the catalog by code + size (`catalogFor`, index `catalog_code`; PK warehouse first); 2026-10-15: 63/76 lines matched — 009-1/009-2 exist in Page365 but not in the SKU+Price sheet, and NI9 has no size 31 (the note was wrong). Next: Page365 has no public API but its web app (cookie session on page365.net, `credentials: include`, 401 → `/session/guard`, request keys snake_cased) uses JSON endpoints: GET `/{page}/orders/{id}.json`, `/conversations/{id}.json` (messages; `customer_fbid` = our Messenger PSID), `/products.json?page=` (751 products, variants carry `code` = our SKU and stock), `/products/{id}.json`; writes POST `/{page}/order_items.json` {order_id, product_ids} (adds each product with its first size), PUT `/{page}/orders/{id}.json` {order: {stage, shipping_cost, discount, …}, order_items: [{id, name, note, price, quantity, product_id = variant id}]}, PUT `/{page}/orders/{id}/advance.json` (the app's "save and send": next stage + sends the bill to the customer), PUT `/{page}/orders/change_stage.json` {orders, stage}. The team prices items at Page365's list price, COD shipping 50, and the promo gap as the bill's discount (3 × 199 + 50 − 98 = 549). Phase 1 (deployed 2026-10-15, `worker/p365fill.ts`): "ใส่ใน Page365" button per note in the Log tab → plan (customer's draft by `customer_fbid` = PSID among drafts ±12 h; product by name starting with the code, variant by SKU ending -size; checks: draft empty, found, in stock, total ≥ 0 discount ≤ 50%, COD matches, no product twice) → on press: add items, set size/qty/price/shipping/discount, read back and compare; the draft stays a draft and an admin still presses save-and-send in Page365 (`advance` is never called). Needs Worker secret `P365_COOKIE` (Cookie header of a logged-in page365.net session, ideally a separate low-rights admin) — set by Benz, never by Claude; first real fills #29349 and #29323 on 2026-10-15, checked in Page365. Phase 2 (Benz 2026-10-15): the plan also checks the note's total against the last "ยอด/รวม … N" the shop wrote in the chat (`chatTotal`; equal or note = chat + COD 50, else stop — the chat price wins), sets the bill name "PK-9349 <recipient>" (warehouse of the first SKU, CN → C, last 4 digits of the bill), and fills the address: Page365's own if complete and clean, else read from the chat by Claude (`worker/addressReader.ts`, typed text + the customer's last 3 photos by URL, structured output; `claude-opus-5-5` at low effort, `ADDRESS_MODEL` to change; the org key needs `ANTHROPIC_WORKSPACE_ID` and doesn't allow the server-side-fallback beta); the admin can correct it in the dialog. Problems stop; warnings (no agreed price in chat, address incomplete/doubtful, tiny discount) allow a single fill but are skipped by "ใส่ทุกใบที่ผ่าน" (browser loops plan → fill). Dry run 15 Oct: 11 of 15 open drafts passed. Addresses are never stored on our side. Missing postcodes (and short province names like นม, typos like ปมุมธานี) are filled/checked from the subdistrict with a built-in address book (`worker/thaiAddress.ts`, data `worker/data/thaiAddressData.ts` from kongvut/thai-province-data, MIT, 7,436 subdistricts; regenerate, don't hand-edit) — for chat-read addresses and for Page365's own; writing via a stored session needs Benz's go-ahead, a low-rights account, and the save requests seen once while an admin does an order. Also ask Page365 for an official API.

## Purchases to Meta
Purchases to Meta from Page365 orders (`worker/metaPurchases.ts`, Benz 2026-10-15: admins stop tagging sales in Meta's inbox once it is live): Conversions API for Business Messaging, POST `/{dataset}/events` with event Purchase, action_source business_messaging, messaging_channel messenger, user_data {page_id, page_scoped_user_id = Page365 `customer_fbid`}, value = bill total THB, event_time = bill opened (keeps hourly crediting in line), event_id `p365-<no>`. Counts: COD from stage unpaid (bill sent), transfer from transferred/paid. Runs from webhook deliveries at most every 10 min (no cron), ≤30 order look-ups per run, last 7 days; table `meta_purchases`, settings `meta_capi` (mode off/test/live, dataset_id, test_code, live_from = when live was switched on — earlier orders were tagged by hand) on the settings page, dry run button. Blocked 2026-10-15: the token has no `page_events` and sees no dataset (`GET /api/meta/datasets`); keep admins tagging until live.

**At the note (default source, Benz 2026-10-15):** the sale is sent seconds after the admin types the note, so it lands on the day/hour the customer agreed (the admins' own "Create order" in Meta's inbox happened at that moment too; sending at the bill put sales on the next day). event_time = note time, value = the note's total, event_id `note-<mid>`, one sale per customer per 2 hours; table `note_purchases`; setting `meta_capi.source` = note | bill (bill = the older bill-stage sender). A sale Meta refuses (status `error`, not retried) is told to the problem channel with the customer and Meta's answer, asking an admin to press Create order in the inbox instead (`sendNoteSale` in `worker/autoFill.ts`; at most one message per 15 min, Benz 15 Oct). Preview on the settings card ("ดูว่าวันนี้จะส่งอะไร"); sends only in live mode, which Benz switches on together with telling admins to stop pressing Create in Meta's inbox. Meta has no API for its inbox orders ("Manage Orders"), so that list stays empty once admins stop; a page of our own for Max is proposed.

**Status 15 Oct evening:** auto-fill on (Benz); purchases live at the note (source note, live_from 2026-10-15T09:08Z); admins no longer press Create order in Meta's inbox nor open drafts themselves. Bills the auto-fill leaves for a person go to Discord channel "ออเดอร์มีปัญหา" (secret `DISCORD_ORDER_WEBHOOK_URL`, tagging เนย — var `DISCORD_ORDER_OWNER_IDS`, Benz 15 Oct; empty = the deciders; test button `POST /api/order-notes/test-discord`), and show the reason on the note's row in the Log tab. The admin's note is the trigger and its total the price; a chat total for this order that disagrees still holds the bill. Warnings only (an address doubt, a small discount) no longer hold it (Benz 15 Oct, #29372 left empty over a name doubt): items, price and any shippable address go in, and Discord says "ใส่บิลให้แล้ว แต่ช่วยเช็ก" with the doubts. The chat is now read on every bill (also when Page365 has the address) with the note alongside, so a customer who cancelled (#29329) or a note size that isn't what the customer asked for (#29367, note 30 / asked 32) stops the bill; a misspelt subdistrict is matched to the closest one in its district (ตลาดตะเคียน → ลาดตะเคียน, #29369) and filled with a "ช่วยเช็ก". Still stopped on purpose: a size the model doesn't make, a chat total that disagrees, a phone that isn't 9–10 digits (items go in, address left for a person). **A draft always (Benz 15 Oct):** every note gets its Page365 draft first, recorded on the note at once ("เปิดร่างแล้ว · รอใส่รายละเอียด"), details after (`ensureDraft` in `worker/autoFill.ts`): the customer's latest order if it is a draft (`last_order_id` from the conversation list), else a draft of theirs within 12 h, else a new one. No second bill for one order: a bill already made/sent around or after the note is taken as the note's; a draft filled from another note of the customer within 2 h = a correction, left for a person; filled from an older note = a new order, new draft (#29364, 16:53). One note per webhook delivery (free-plan request limit); `sweepNotes` (deliveries without notes, every 5 min, notes since 2026-10-15 16:00 Bangkok, last 24 h) retries notes never started, cut short (gives up after 3) or waiting for a Page365 login; an expired login posts once an hour to the problem channel. The sweep also re-reads stored shop messages (`chat_messages`) for notes the parser missed and stores them (and sends their sale at the note time) — so a parser fix catches up by itself ("โอน349kb / 301/1 sz34 2ตัว", 15 Oct: bank after the total and "2ตัว" now read). A repeated summary for a bill already sent (16:53 ภิรมย์ → #29364, which an admin had just marked paid; an extra draft was opened and deleted by an admin) is now recognised: the customer's latest bill counts as this order when another note of theirs within 2 h went into it. ## Order-note formats

Every format the admins have typed is kept in `worker/noteFormats.test.ts` (Benz 15 Oct: when a format is fixed, keep it). A missed or misread note → add its real text and what it should read as there, then fix `parseOrderNote`; all of them must keep passing. Read today: codes with colours `501/1/2/3`, `Ni9-1-2-5`, `009-1-2`, `16-9 , 16-10`, several codes `D01 D02`, `200 200/2`, one line per model; size `32`, `sz34`, `size`, `w`, `เอว`, `ไซส์`, or a size line of its own under a list; quantity after the size `2`, `2ตัว`, `2 ชิ้น`, `x3`; list style `- สีเทา (16-10) 1 ตัว`; payment `cod`/`โอน`/`ปลายทาง` + total at the end or first, with or without a space, `บาท`, or the bank (`kb`, `kbank`, `scb`, `กสิกร` …); a stray letter on a numeric code (`E200` → 200) is retried by the fill. Never notes: anything with an address, a name, a phone number or chat text. **Misses (Benz 15 Oct):** a shop message that looks like a note (cod/โอน + total + something code-like, ≤ 150 chars, no phone/postcode/address words/คุณ) but isn't read (`looksLikeNote`) goes to `note_misses` and to the problem channel once ("ข้อความนี้เหมือนสรุป แต่ระบบอ่านไม่ออก", no draft or Meta sale yet), from the webhook at once and from the sweep for anything stored. Log tab: "สรุปที่ระบบอ่านไม่ออก". Learning loop: add the miss to `noteFormats.test.ts`, fix the parser, deploy → the next sweep (≤ 3 h) reads it from the stored chat, opens/fills the bill, sends the sale at the note's time, and marks the miss read. Checked on 380 shop messages of 13–15 Oct: 0 false alarms.

**Fixes from the 15–20 Oct review (Benz 20 Oct, 438 auto-filled bills compared with Page365; admins changed items on 5, totals on 3):** banks mean โอน (`kb 399`, `kb โอน499`, `KB โอน 998`); keyboard left in Thai (`หผ34`, `ทi9`, `3ตัส`); colours split by either separator (`ni9-1/3/4`); products picked by `pickProduct` (same code, other separators when the code has one or letters — `009/1` = 009-1, `SK004` = SK-004 — or a colourless code's only colour, `205` = 205/1; `204` never matches `20-4`); the same model in several sizes is filled (one item per size, read-back checks it); the house-number line loses the recipient's name and phone (`cleanStreet`, 10 + 3 bills had them). Waiting for Benz: size ≥ 38 +60, splitting mixed-warehouse bills, sizes 29/31/33 not made, chat total vs note (27 stops, admins kept the note's total every time), a second note within 2 h as a correction, CN letter sizes, 980/C01 colours.

**Benz's answers, 20 Oct (applied):** (1) sizes ≥ 38 cost +60 a piece except NI9 — a warning when the chat didn't agree that exact total; also in the Business AI answer bank. (2) Mixed-warehouse orders stay one bill (discount and COD fee on it). (3) A size the customer asked for that isn't made (29/31/33) doesn't stop the bill (`askedSizeNotMade`); the bot should offer a made size (answer bank). (4) The note's total is the price — a chat total that differs is a warning, not a stop (special prices for hagglers). (5) A corrected summary within 2 h replaces the earlier draft (delete + reopen + fill; only with cleanup on). (6) CN models are written with letter sizes (`SH-001 2XL`). (7) Colour names work as well as colour codes: `980 ดำกรม 1` (= 980-31; team names that differ from Page365's go in `COLOUR_ALIASES`, p365fill.ts), `980 freesize`, `980-32` alone, and colour lines under a code (`C01 L` / `ดำแดง1`). (8) Notes missing a quantity or colour keep stopping. (10) `draftCleanup.ts`, switch on the Log tab (ships off, Benz switches it on after the preview): a draft the chat reader thought cancelled is deleted only if still unsent after 7 days (the reader was wrong on all 5 "cancelled" orders of 15–19 Oct; a possible cancel is now a warning — filled, person asked — and remembered as `meta_capi` `cancel_hint:<no>`); a draft still without phone/postcode or empty is warned at day 5 and deleted at day 7; runs in the 3-hourly cron; never touches a bill that has moved on.

**Accuracy, measured daily (Benz 20 Oct, `worker/fillAudit.ts`, table `fill_audit`, migration 0052):** each note's bill, once it has moved on in Page365 (or is 7 days old, or gone), is compared with the note — the 20 Oct hand check, automated. Outcomes: `ok` / `edited` (size, items, qty, total, payment) for bills the system filled; `stopped_kept` (the person ended with what the note said: the stop wasn't needed) / `stopped_changed` for bills it stopped, with the stop reason grouped (`stopReason`); `deleted`; `open` (still a draft, checked again after 12 h). Address flags: phone/name in the street line, no phone, no postcode. Runs a few bills per webhook delivery when there is nothing to sweep (≤ 10 per 10 min) and once more at 09:15 Bangkok, when yesterday's numbers go to the problem channel. Log tab card "ความแม่นยำใส่บิล (7 วัน)"; `GET /api/order-notes/accuracy?days=`, `POST /api/order-notes/audit-run` (one step by hand). Weekly loop: look at the numbers on Monday, fix the top stop reason, add new note formats to `noteFormats.test.ts`.
